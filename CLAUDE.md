# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Справочник польской грамматики на русском. Статический сайт на GitHub Pages (`polski.hamanovich.com`), собирается из данных в предгенерированные HTML-страницы.

## Команды

```sh
npm install          # linkedom - единственная зависимость, нужна только для сборки
npm run build        # генерирует index.html, */index.html, 404.html, search-index.js, sitemap.xml, fulltext.txt
npm run og           # перерисовывает og/*.png и og/manifest.json (нужен Chrome, запускается вручную)
npm run lint         # scripts/lint-content.mjs: запрещённые символы в исходниках и в выводе
npm run check        # node --check по всем скриптам + npm run lint + scripts/check-build.mjs
npm run drift        # git diff по сгенерированным файлам: они разошлись с исходниками?
npm run verify       # build + check + drift, то же самое гоняет CI
open index.html      # сайт работает по file://, сервер не нужен
```

Тестов как таковых нет: их роль играет `scripts/check-build.mjs` - набор `assert`'ов по сгенерированному HTML. Отдельного теста запустить нельзя, только весь файл. Многие проверки - жёстко зашитые числа и цитаты контента (404 строки словаря, 100 ложных друзей, 14 вариантов падежей, 21 ссылка в оглавлении, `assert(searchIndex.length > 1500)`). При правке контента их обновляют вместе с данными - это не поломка, а намеренный «замок» на объём.

**Всегда `npm run build && npm run check` после правки `data.js`, `app.js`, `client.js`, `index.template.html` или `style.css`** - иначе закоммиченный HTML и хеши ассетов разъедутся с исходниками.

`npm run verify` доводит это до конца: собирает, проверяет и требует, чтобы `git diff` по сгенерированным файлам был пуст. Он падает и когда исходники правили без пересборки, и когда пересобрали, но не сделали `git add` результата. `plan-40/index.html` из проверки исключён: он написан руками и сборкой не переписывается. То же самое гоняет `.github/workflows/ci.yml` на каждый push и pull request.

### Git-хуки

Хуки лежат в `.githooks/` и коммитятся. `npm install` через скрипт `prepare` прописывает `git config core.hooksPath .githooks`, поэтому husky не нужен. Если хуки не срабатывают, проверь `git config core.hooksPath`.

- `pre-commit`: `node --check` по `data.js` и `app.js`.
- `pre-push`: `npm run verify` целиком, то же самое, что в CI. Падение блокирует push; пересобранные файлы уже лежат в рабочем дереве, обычно достаточно `git add -A && git commit --amend --no-edit`. Обойти: `git push --no-verify` или `SKIP_VERIFY=1 git push`.

`scripts/lint-content.mjs` сторожит правило «никаких длинных тире»: он обходит все `.js`, `.mjs`, `.html`, `.css`, `.md`, `.txt` вне `node_modules` и `og` и падает на U+2014 и на неразрывном пробеле U+00A0. Сами запрещённые символы записаны в нём escape-последовательностями, иначе он ловил бы себя. Короткое тире U+2013 разрешено: им набраны числовые диапазоны (`0-20`, `pn.-pt.`).

## Архитектура: сборка и рантайм - разные миры

Ключевая вещь, которую не видно из одного файла: **`data.js` и `app.js` в браузер не попадают.** `scripts/build.mjs` поднимает DOM через linkedom, выполняет оба файла в `node:vm`-песочнице с заглушками (`matchMedia`, `localStorage`, `location`, `history`, `getComputedStyle`), даёт им отрисовать весь контент в `index.template.html` - и затем **вырезает их `<script>`-теги** из результата. В браузере остаётся только `client.js`.

Отсюда следствия:

- `app.js` - это шаблоны контента (`renderCase`, `renderVerbs`, `renderTalk`, ...) плюс исторический слой SPA-логики (`showTab`, `search`, `applyTheme`, `hashFor`). Второй слой при сборке выполняется, но в браузере мёртв. **Правка поведения на живом сайте - это `client.js`, а не `app.js`.**
- Хелперы дублируются в обоих файлах (`norm`, `clean`, `scrollToHeading`, `applyHash`, темы, поиск). Меняя один, проверь, нужен ли парный.
- Всё, что песочница не умеет (реальные размеры, `IntersectionObserver`, анимации), при сборке молча ничего не делает - контент от этого зависеть не должен.

### Как build.mjs делает страницы

1. Рендерит один «мастер»-DOM из `index.template.html`: все 22 секции заполнены.
2. Пишет `fulltext.txt` (текст мастера без `.practice`) и `search-index.js` (по секциям, пропуская `.practice`; каждому найденному узлу проставляется `id="r-N"`, на который потом ссылается поиск).
3. Для каждого маршрута клонирует мастер, **удаляет все `.sec` кроме своей**, подставляет title/description/canonical/og, подсвечивает группу в навигации, дописывает пейджер «предыдущий/следующий» и переписывает все `data-s`-ссылки в настоящие относительные пути (`../verbs/`).
4. Старые ссылки `#s-verbs/czasy` переписываются `modernHash()` в новые адреса; `check-build` требует, чтобы ни одной `a[href^="#s-"]` не осталось.
5. `style.css`, `client.js` и `search-index.js` получают `?v=<sha256:10>` - fingerprint считается от содержимого, поэтому ассеты кешируются навечно.

### SEO-разметка

Список страниц живёт в `scripts/pages.mjs` и импортируется и сборкой, и генератором OG-картинок.

`h1` каждой страницы задаётся полем `h1` в `pages`, а не берётся из контента. На обычных страницах он заменяет первый `h2` секции; на `cases` и `verbs`, где первый `h2` лежит внутри `.content-variant` и меняется при переключении, `h1` добавляется в начало секции, а заголовок варианта остаётся `h2` (его размер понижен правилом `.verb-variant > .panel > h2:first-child`).

В `<head>` каждой страницы сборка кладёт один блок `application/ld+json`: `WebSite`, `WebPage` (+ `LearningResource`, на главной `CollectionPage`) и `BreadcrumbList` из двух шагов. Хлебные крошки намеренно двухуровневые: у групп из `GROUPS` нет своих страниц, а промежуточный шаг без URL Google не принимает. `dateModified` и `lastmod` в sitemap - **своя дата у каждой страницы**, она живёт в `content-manifest.json` (см. ниже).

### Даты страниц: content-manifest.json

`content-manifest.json` - коммитимый файл вида `ключ: {hash, date}`, по записи на каждую страницу (ключ - `path`, у главной `index`) плюс `plan-40`. `hash` - sha256 готового HTML страницы, в котором замаскированы `?v=<fingerprint>` и сама дата (в разметке она собирается через плейсхолдер `__CONTENT_DATE__`). Сборка считает отпечаток и сравнивает с манифестом: совпал - берётся дата из манифеста, разошёлся - ставится сегодняшняя, и манифест перезаписывается. Для `plan-40` хешируется сам файл-исходник.

Что из этого следует:

- Правка `data.js` двигает `lastmod` только у тех страниц, чей контент реально изменился, а не у всех 22 сразу. Для Google это разница между сигналом и шумом.
- Смена `style.css` или `client.js` меняет `?v=` во всех файлах, но дату не двигает: fingerprint из отпечатка вымаран.
- Даты в git не считаются вообще. Раньше `dateModified` брался из даты последнего коммита, тронувшего контент, - а собирали-то до коммита, поэтому в HTML попадала дата *предыдущего* контентного коммита. Совпадало только если оба коммита пришлись на один день, и каждая правка контента в новый день роняла `drift` в CI. Теперь дата замораживается в момент сборки и лежит в манифесте, CI её не пересчитывает.
- Если манифеста нет, даты подхватываются из уже лежащего `sitemap.xml`, чтобы его пересоздание не проставило всем сегодняшнее число. Сегодняшняя дата - только для страниц, которых в старом sitemap не было.
- `check-build.mjs` требует, чтобы манифест покрывал ровно все страницы, а `lastmod` в sitemap и `dateModified` в JSON-LD совпадали с ним.

### Варианты вместо вкладок

Падежи и подразделы глаголов отрисовываются **все сразу** в `.case-variant` / `.verb-variant` внутри `.variant-host`; `client.js` только переключает класс `.on`. Без JavaScript CSS показывает их все подряд - страница остаётся читаемой. `check-build.mjs` следит за этим правилом прямо в CSS: `.sec{display:block}`, `.js .sec{display:none}`, `.content-variant{display:block}`, `html:not(.js) .navpop{display:block}`. Эти селекторы нельзя переименовывать не обновив проверку.

### Упражнения

Блоки `.practice` (интерактивные задания и тесты, `exerciseTestHTML`) исключены и из `fulltext.txt`, и из поискового индекса. Ответы пользователя лежат в `localStorage` под ключом `polski-exercises-v1`.

## Список разделов живёт в пяти местах

Добавление раздела - это правка всех сразу:

| Где | Что |
|---|---|
| `data.js` | массив с данными; запись в `TABS` (id → подпись) и в `GROUPS` (порядок чтения, группы навигации, пейджер, оглавление) |
| `app.js` | функция `render*()` + вызов в блоке «СТАРТ» внизу файла |
| `index.template.html` | пустая `<section id="s-…" class="sec">` |
| `scripts/pages.mjs` | запись в `pages` с `path`, `h1`, `title`, `description` (маршрут, canonical, sitemap, JSON-LD, OG-картинка) |
| `scripts/check-build.mjs` | запись в `routes` (`id`, `path`, ожидаемый `h1`) + при желании контентный `assert` |

`GROUPS` задаёт порядок чтения и группировку независимо от порядка `TABS`.

### Оглавление внутри страницы

`linkHeadings` в `app.js` вешает на каждый `h3` вне `.content-variant` настоящий `id` вида `~slug` - тот же slug, что уже лежит в `data-h`. Благодаря этому ссылка `/questions/#~общии-вопрос-czy` работает нативно, без JS, и годится Google под «Перейти к разделу». Внутри вариантов `id` не ставится: заголовки там повторяются от варианта к варианту, и это дало бы дубли `id` на странице.

Если таких заголовков в разделе набирается `TOC_MIN` (пять) и больше, `build.mjs` вставляет после вводного абзаца блок `nav.toc`. Порог продублирован в `scripts/check-build.mjs`, менять его надо в обоих файлах. Сейчас это тринадцать страниц: `adjectives`, `adverbs`, `alphabet`, `conjunctions`, `diminutives`, `gender`, `numerals`, `particles`, `people`, `pronouns`, `questions`, `speaking`, `word-order`. На `cases` и `verbs` оглавления нет намеренно: их подразделы лежат в вариантах, роль оглавления там играют чипы.

### OG-картинки

`npm run og` рисует `og/*.png` (1200x630) через headless Chrome: заголовок берётся из поля `h1`. Скрипт намеренно не входит в `npm run build` - Chrome не должен становиться зависимостью сборки, а картинки нужно перерисовывать только когда меняется `h1`. PNG коммитятся. `check-build.mjs` проверяет, что для каждой страницы файл на месте.

Разметка карточки живёт в `scripts/og-card.mjs` и импортируется и генератором, и проверкой. Рядом с PNG лежит `og/manifest.json`: для каждой карточки в нём хранится sha256-отпечаток её HTML. `check-build.mjs` пересчитывает отпечатки и требует совпадения, поэтому изменение `h1` в `pages.mjs` или самого шаблона карточки роняет `npm run check` с подсказкой `rerun npm run og`. Без этого устаревшая картинка живёт молча до первого репоста.

## Генерируемые файлы - коммитятся, руками не правятся

`index.html`, `*/index.html` (21 тематическая страница), `404.html`, `search-index.js`, `sitemap.xml`, `fulltext.txt`, `content-manifest.json`. Отдельно - `og/*.png` и `og/manifest.json`: их пересобирает не `npm run build`, а `npm run og`. Они в репозитории намеренно: GitHub Pages раздаёт их без Node.js. Наружу при этом уходят не все: `fulltext.txt` и `content-manifest.json` собираются и коммитятся, но закрыты в `_config.yml` и по прямой ссылке не открываются. Любая правка - через `data.js`/`app.js` + `npm run build`.

Исключение: **`plan-40/index.html` написан руками**, в `pages`/`routes` не входит и сборкой не переписывается. В sitemap он всё же попадает - через `extraPages` в `scripts/pages.mjs`, с датой из `content-manifest.json` по отпечатку самого файла. Из-за этого его `canonical`, `og:*` (включая `og:image`) и блок JSON-LD правятся вручную и заперты отдельными `assert` в конце `check-build.mjs`. Стили страницы лежат в `style.css` в блоке `body.plan-page`.

## Что отдаётся наружу: _config.yml

GitHub Pages собирает сайт «legacy»-режимом, то есть через Jekyll (`build_type: legacy`, ветка `main`, корень). Значит наружу по умолчанию уезжает **весь репозиторий**, включая исходники и служебные файлы: до появления `_config.yml` по прямой ссылке открывались `LINGUIST.md`, `CLAUDE.md`, `AGENTS.md`, `README.md`, `data.js`, `app.js`, `index.template.html`, `package.json` и `scripts/build.mjs`.

Список `exclude` в `_config.yml` держит их закрытыми: Jekyll просто не копирует эти пути в опубликованный сайт, и они отдают 404. Файлы и папки, начинающиеся с точки или подчёркивания (`.github`, `.githooks`, сам `_config.yml`), Jekyll не публикует и без списка.

Ставить `.nojekyll` нельзя: он выключает Jekyll вместе с `exclude`, и всё снова станет публичным.

`check-build.mjs` держит это замком с двух сторон: любой новый файл или папка в корне обязаны быть либо в белом списке `publicRoot`, либо в `exclude` (иначе `npm run check` падает с именем файла), и ничего из `publicRoot` не должно попасть в `exclude`. `robots.txt` тут не помощник: он про индексацию, а не про доступ.

## Соглашения по контенту

Роль лингвиста-аудитора описана в `LINGUIST.md` в корне репозитория: критерии качества, обязательный фактчекинг, приоритеты находок и формат аудита. Читай её до работы над учебным содержанием. Аудиты лежат в `_audit/<SECTION>-LINGUIST-AUDIT.md`, коммитятся и наружу не публикуются.

- Язык интерфейса и объяснений - русский, с опорой на русский и белорусский.
- Никогда не писать комментарии в коде.
- **Никаких длинных тире.** Символ длинного тире (U+2014) не использовать нигде: ни в `.js`, ни в `.html`, ни в `.css`, ни в `.md` - ни в данных, ни в разметке, ни в заголовках и description страниц, ни в комментариях, ни в сообщениях коммитов. Вместо него - дефис `-` с пробелами вокруг, запятая, двоеточие или скобки. Плейсхолдер «формы нет» в ячейке таблицы - голый `-` без пробелов (с ним в паре идут компараторы в `app.js`: `p[3] === "-"`, `v[8] === "-"`). Это осознанный выбор оформления, а не следствие автоформатера: правку в обратную сторону не делать. Правило проверяется автоматически: `npm run lint` внутри `npm run check`.
- Классы разметки в шаблонах `app.js`: `.pl` - польское слово, `.w` - форма/ключевое слово в ячейке, `.g` - пример, `.note` - пометка мелким, `.lead` - вводный абзац, `.tip` - выделенная врезка, `.vt` - таблица с шапкой, `.scroll` - обёртка для горизонтальной прокрутки таблицы, `.panel` - карточка раздела.
- Данные в `data.js` - массивы массивов (кортежи), а не объекты; порядок колонок определяется соответствующей `render*()`-функцией.
- Подзаголовки `h3` получают якоря автоматически (`linkHeadings`: `data-h` = slug из текста + кнопка «скопировать ссылку»). Адрес выходит вида `/verbs/#~управление`, на страницах падежей и глаголов - `/cases/#dop/pl/~slug`. Slug привязан к тексту заголовка, поэтому переименование h3 ломает внешние ссылки.
